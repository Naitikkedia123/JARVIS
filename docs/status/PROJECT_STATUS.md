## Phase 04 — Typed Tool Registry and Permission Policy (implementation and validation complete)

- Implemented typed tool contracts and a registry populated only by trusted application code. Dispatcher construction seals registration. A separate default-deny policy uses trusted authorization context; model-generated requests cannot provide identity or capabilities. Dispatch validates inputs and outputs and enforces bounded timeouts and result sizes.
- Added structured audit events for authorization and dispatch outcomes. Audit metadata excludes raw arguments, outputs, credentials and exception messages. The provided in-memory audit sink is non-durable; its records are lost when the process exits.
- Pass B1 added a local-only status tool and workspace list/read/create operations using an injected, validated workspace root. Requests cannot override the root. Paths are restricted, reads and writes are byte-limited, creation is exclusive, and writes require both `workspace:write` and `tool:write`.
- Workspace-root initialization checks the original path for symlinks and Windows reparse points and compares filesystem identity across validation steps. Operations recheck the retained root identity. Path-based operations do not eliminate races from a hostile concurrent local filesystem replacement; the configured workspace must be trusted against concurrent local mutation.
- Pass B2 added typed, in-memory pending approval requests for tools that require approval. The dispatcher validates and authorizes before creating a request from trusted tool metadata and principal context, then raises a typed approval-required outcome without invoking the executor. There is no approval UI, trusted decision channel, durable storage, expiry workflow, or execution-after-approval path. If audit recording fails after request creation, a pending in-memory request may remain, but the executor is not invoked.
- Independent review results: Pass A final review **PASS WITH FINDINGS**, with core authorization and auditing controls confirmed; Pass B1 final review **PASS WITH FINDINGS**, with no blocker or high-severity issue and its narrow filesystem TOCTOU limitation documented; Pass B2 review **PASS WITH FINDINGS**, with no blocker or high-severity issue and the audit-failure behavior documented.

The two skipped tests require symlink creation, which Windows policy denied in that environment; those scenarios were not dynamically tested. ## Phase 05 — Memory v1 (implemented, reviewed, validated and accepted)
- Added typed, strictly validated task episode, explicit preference, project fact and artifact-reference records with UTC timestamps, provenance, confidence, scope, sensitivity, permission, validity, expiry, version and supersession metadata.
- Added an injected-path SQLite store with the separate `memory_schema_migrations` ledger, foreign-key enforcement, bounded busy timeout, ordered transactional migrations, transactional corrections/deletion, optimistic version checks, and a bounded retrieval layer that enforces scope, sensitivity, permission, provenance, lifecycle and validity constraints in SQL.
- Legacy rows migrate without loss of content and receive `legacy_unknown` provenance, `legacy_inaccessible` scope, restricted sensitivity and unspecified permission. They remain inaccessible through normal retrieval until separately governed.
- Full-text retrieval uses SQLite FTS5 when available and a parameterized, escaped `LIKE` fallback otherwise. Metadata filters and full-text results share the same access-control and current-validity filters. Correction preserves the previous version as superseded; deleting a replacement does not reactivate its predecessor. Deletion removes the selected database row and its search entry.

## Phase 06 — Research, Sources and Browser Tools (accepted)
- Passes A–D provide typed research request/result/source models and the read-only `browser.research` tool through the existing registry, dispatcher and default-deny authorization policy. Trusted initialization supplies the fetcher and exact per-host IP allowlists; each fetch validates DNS and pins the connection to an approved numeric IP while preserving the original hostname for TLS and HTTP identity.
- Retrieval uses a TLS 1.2 minimum, certificate-chain and hostname verification with the system trust store, and an explicit cipher policy for TLS 1.2 and earlier; TLS 1.3 remains governed by platform/OpenSSL defaults. Redirects, environment proxies and keep-alive reuse are disabled. Network time and streamed response size, extracted text, titles, excerpts and summaries are bounded. Errors are normalized safely; source metadata and provenance are retained, retrieved content remains untrusted, and audit payloads omit URLs and page content.
- Passes A–D received independent security reviews. The owner accepted Phase 06 after those passes and reviews. Latest owner-reported Python 3.13.1 validation: focused browser tests, 59 passed; full suite, 239 passed and 2 skipped; Ruff and whitespace checks passed. The run reported one existing Starlette/httpx deprecation warning. The skipped symlink tests require symlink creation, which the current Windows policy blocked; those scenarios were not dynamically tested.
- Tests used mocked DNS and HTTP/TLS transport; no real DNS/network request or live TLS handshake was used. Trusted exact IP lists need deliberate review when CDN addresses change and must not be expanded automatically. The default OS `getaddrinfo` work may continue in its executor thread after the caller's timed wait expires. An explicitly approved endpoint could later become hostile or compromised. Application controls do not guarantee comprehensive SSRF protection; host and network egress controls remain useful independent safeguards.
- Phase 06 is accepted but remains uncommitted, unpushed, unmerged and unreleased on `feat/research-browser-tools`. This does not claim that JARVIS is a complete autonomous assistant. The next phase remains pending separate owner direction.
