# Phase 00 — Feasibility report

**Research snapshot:** 2026-10-17
**Scope:** architecture and feasibility only; no runtime feature, dependency installation, model download, account access, integration, cloud resource, or paid service was used.
**Recommendation:** JARVIS-owned Python control plane with selective, narrow adapters; see [ADR 0001](../decisions/0001-architecture-choice.md).

## Executive finding

Option B best fits JARVIS's full vision. OpenClaw is the strongest ready-made integration candidate and is materially easier to evaluate as an external local Gateway than as a fork. Its Windows, Android companion, model-provider, and messaging breadth is valuable, but its own documentation describes a trusted single-operator Gateway with powerful host/plugin trust. That makes it a component to wrap carefully, not a substitute for JARVIS policy, durable-goal semantics, memory provenance, or verified task completion.

Building everything directly (C) gives maximum control but also puts all provider, desktop/mobile, channel, security, and maintenance work on JARVIS. It is less attractive for the stated goal of evolving a useful assistant on an 8 GB laptop without mandatory recurring costs. Open Interpreter, OpenHands SDK, Letta Code, and LangGraph are credible references or future specialized components; none removes the need for JARVIS to own its authority model.

The weighted option comparison is in the ADR. The weights total 100%; scores are qualitative estimates, not benchmark results.

## Evidence labels and limits

- **Verified fact:** directly stated in an official repository, product documentation, platform API documentation, or local project document linked here.
- **Estimate / inference:** engineering judgment based on those facts; it is not a measured result or vendor promise.
- **Assumption:** a planning premise that has not been checked on the actual machine/account/device.
- **Unresolved:** requires a later, explicitly scoped check or a live entitlement/device view.

Official pages and repositories below were accessed on **2026-10-17**. Where release pages exposed publication dates, they are listed. Most rolling `main` branch docs and product pages did not expose a publication date in the inspected view, so their access date is the snapshot date. Repository license labels were cross-checked against the repositories' `LICENSE` files where available. A release in the recent history is evidence of recent published activity, not a guarantee of future maintenance or support.

No runtime benchmarks or integration proof-of-fit tests have been performed.

### Why an external local OpenClaw Gateway is the first integration candidate

**Verified:** OpenClaw documents a standalone Gateway, local interfaces, an HTTP compatibility surface, extensive channels, Windows node features, a persistent background-task ledger/cron run history, and a Windows Hub mode that can expose a local MCP server. Its optional memory-wiki documents claim/evidence/provenance metadata and freshness/contradiction checks. **Estimate:** consuming a stable external interface is likely easier to maintain than forking the whole product because JARVIS can avoid owning upstream merges and release engineering. An adapter still needs protocol/version compatibility and must translate only a narrow JARVIS-approved capability set.

Important limitation: OpenClaw's security documentation places authenticated Gateway callers in the trusted-operator class and warns that local/same-gateway sessions are not a strong per-user authorization boundary. Its HTTP compatibility and tool invocation endpoints share that broad trust model. Therefore, a Gateway token is effectively a sensitive operator credential. Keep any future Gateway loopback/local, never pass that credential to a model or page content, and have JARVIS policy authorize each adapter operation. A fork should be considered only if a required boundary cannot be implemented through a supported external interface and the project accepts the security/update maintenance. ([Gateway API](https://github.com/openclaw/openclaw/blob/main/docs/gateway/openai-http-api.md), [SECURITY.md](https://github.com/openclaw/openclaw/blob/main/SECURITY.md), [Windows Hub MCP mode](https://github.com/openclaw/openclaw/blob/main/docs/platforms/windows.md))

## Platform and device feasibility

### Windows UI automation

**Verified:** Microsoft's UI Automation (UIA) is a Windows accessibility and automated-testing API. It exposes programmatic information and interactions for most UI elements, through provider support and control patterns. An application's provider must expose the controls; custom or unsupported controls may not expose every behavior. This makes UIA a reasonable first Windows automation surface for stable, accessible controls, but it does not prove every desktop app or canvas can be controlled reliably. ([Microsoft UI Automation overview](https://learn.microsoft.com/en-us/dotnet/framework/ui-automation/ui-automation-overview), published 2021-09-15; [UIA testing overview](https://learn.microsoft.com/en-us/dotnet/framework/ui-automation/using-ui-automation-for-automated-testing), published 2021-09-15)

**Estimate:** keep automation in a separate, allowlisted Windows node with visible consent and verification. Use UIA first; treat image/mouse fallback as a more brittle last resort. A later proof must check the actual target app's UIA tree, control patterns, elevation boundary, unexpected dialogs, and recovery behavior. Phase 00 did not run desktop automation.

### Android, call roles, and audio

**Verified:** OpenClaw's Android application is a paired companion node; it requires a Gateway on another supported host. That is useful evidence for an adapter route but is not proof that OpenClaw meets JARVIS's pairing/security contract. ([OpenClaw Android](https://github.com/openclaw/openclaw/blob/main/docs/platforms/android.md))

Android's official Telecom API documents `CallScreeningService` for the user-selected call-screening app. It can receive call details for incoming calls before ringing and outgoing calls, and must respond to an incoming call within five seconds. The default dialer role is different: it requires a full dial-pad and in-call UI. These APIs are conditional on the role the user grants and platform behavior; they do not establish that an ordinary companion can autonomously control calls. ([CallScreeningService API](https://developer.android.com/reference/android/telecom/CallScreeningService), [default phone app requirements](https://developer.android.com/develop/connectivity/telecom/dialer-app))

Android's media guidance says call audio is delivered to the call; an ordinary app cannot capture it as a general rule. Capturing voice-call uplink/downlink is limited to privileged preinstalled apps with `CAPTURE_AUDIO_OUTPUT`; an accessibility service has a distinct narrowly described audio-input case, not a general guarantee of recording both sides of cellular calls. ([Android audio input sharing](https://developer.android.com/media/platform/sharing-audio-input))

**Unresolved:** the user's phone model, Android/API level, OEM build, carrier/SIM, default dialer, Bluetooth route, region, and role availability have not been checked. Actual phone verification is required before promising call state, screening, call control, or call audio. No call recording or calling feature is claimed.

### Laptop-phone connectivity

**Verified:** WireGuard publishes clients for current Windows and Android, and its official documentation describes public/private keys, peers, and optional persistent keepalives for peers behind NAT/firewalls. ([WireGuard installation](https://www.wireguard.com/install/), [quick start and NAT guidance](https://www.wireguard.com/quickstart/))

**Estimate:** local Wi-Fi plus authenticated pairing is the least-complex first development path. For remote access without a paid relay, a self-managed WireGuard endpoint is a candidate, but it requires a reachable endpoint, key rotation/revocation, firewall/NAT work, and device-loss handling. This is not a configured integration. Do not expose FastAPI/Gateway directly to the public internet. Hosting or relay services can introduce recurring costs; no specific provider is selected.

## Models, cost, and the coding-agent tools

### Model cost and local inference

**Verified:** the project architecture requires a local-first, provider-neutral interface and explicitly prohibits paid fallback. OpenClaw, Open Interpreter, LangGraph, and Letta support provider choice or local execution paths in their docs, but those options still require compatible local hardware/model software or a provider account. Hosted inference can create a charge; model access entitlement and API billing are distinct.

**No-download benchmark plan:** no honest tokens/second or peak-RAM result can be produced without selecting and running a particular model, quantization, runtime, prompt/context size, and CPU/GPU path. Phase 00 therefore records no local-inference performance number. Before downloading weights in a separately approved phase:

1. Record actual idle/normal-work RAM pressure, CPU load, free disk, and Windows memory commit on the laptop; the plan's i5-1335U/8 GB figures have not been independently remeasured here.
2. Shortlist only small models whose official model cards and runtime documentation publish supported quantization/context and memory considerations; do not infer performance from parameter count alone.
3. Agree a fixed test prompt set and required context length. After model download is explicitly authorized, record cold start, first-token latency, generation speed, peak process/system memory, and output quality for the same prompts; repeat enough runs to see variance and compare with a deterministic hosted/mock path only if no billing-enabled service is involved.
4. Keep a no-model baseline and stop if Windows becomes unstable or the agreed latency/RAM limit is exceeded. Defer Docker/VMs and any second model process on this 8 GB machine.

This is a proposed measurement method, not a benchmark or an estimate. No weights were downloaded and no inference runtime was installed.

**Verified from Google's official Antigravity docs:** the VS Code extension runs on Windows and its sign-in determines model entitlements and limits. **Unresolved:** no Google account or IDE panel was opened. The user's stated Google One/Google AI Plus entitlement is not assumed to be Google AI Pro or Ultra. The current live plan/model/usage view and any account-specific setting remain unverified. To prevent charges/credit use, inspect the signed-in extension's Settings/usage view yourself, keep AI Credit Overages set to **Never** if shown, do not purchase credits or enable auto-reload/automatic credit use, and stop when baseline quota is exhausted. If the UI does not expose a clear “Never” state, do not continue with that account until the setting is understood.

## Cost and resource conclusion

None of the recommended core options inherently requires a paid hosted control plane: a Python/FastAPI/SQLite JARVIS core, open-source libraries, a local Gateway, and local storage can be run on existing hardware. That does not establish total zero operating cost. Electricity, internet, a future public endpoint/relay, commercial API access, platform messaging APIs, and commercial-hosting products may have costs or usage terms. Avoid these by default; never silently fall back to paid inference or paid hosting. Any future networked communication scope must be checked against the official provider API and user-approved account scopes.

The 8 GB constraint favors a small local monolith, SQLite, a single running model/agent process at most, and deferring Docker, Android emulators, databases, and large models. This is a design recommendation based on the stated machine profile, not a measured guarantee that a future workload will fit. Record actual memory/CPU before choosing an inference runtime or background services.
