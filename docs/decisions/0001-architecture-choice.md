# ADR 0001 — JARVIS-owned control plane with selective adapters

- **Status:** Accepted
- **Date:** 2026-10-17
- **Decision owner:** JARVIS project owner

## Context

JARVIS is intended to own its durable goals and tasks, policy and permissions, model-routing rules, memory contracts, audit trail, and completion verification. The target is a Windows-first local system, with an Android companion, that can evolve across model providers without a mandatory recurring software, hosting, or inference bill. The development laptop has 8 GB RAM according to the project plan. No local model benchmark or integration proof-of-fit was run in this phase.

The question is whether to adopt an existing assistant as the control plane, keep control-plane ownership in JARVIS while reusing components behind adapters, or build every required integration ourselves.

## Requirements and scoring method

Scores are ordinal judgments from 1 (poor fit) to 5 (strong fit). The weighted total is `sum(weight × score) / 100`, on a 1–5 scale. Weights reflect JARVIS's stated full vision, with ownership, security, durability, and cross-device reach ahead of initial convenience. All options are evaluated as architectural directions, not as already implemented products. In particular, a high score for option B means the architecture can preserve the requirement; it does not mean the currently scaffolded JARVIS already provides that capability.

The evidence in each score cell is a short rationale. Project capability statements are linked to current official repositories/docs. Statements about likely engineering effort, fit, resource use, or future reliability are explicitly judgments, not measured results.

## Options considered

### A — Extend OpenClaw

OpenClaw is the most complete ready-made personal-assistant candidate reviewed: it documents a local Gateway/control plane, model providers, extensive messaging channels, nodes, Windows support, an Android companion, and optional provenance-rich memory-wiki functionality. It is MIT-licensed and actively released as of this review. It is therefore the strongest option for a quick channel/device proof-of-fit.

Its documented trust model is a material fit limitation: a Gateway is for a trusted operator, not an adversarial multi-tenant boundary; an authenticated Gateway caller receives broad operator capability, host execution is the default absent sandbox configuration, and plugins are trusted code in the Gateway process. Those are explicit design choices rather than claims that OpenClaw is unsafe for its intended single-user use. OpenClaw does have persisted task tracking and scheduling, plus provenance-rich optional memory tooling; these capabilities still use OpenClaw semantics and do not automatically make JARVIS's own policies authoritative. Its Android app is a paired node, not a phone-hosted Gateway. See the [official security policy](https://github.com/openclaw/openclaw/blob/main/SECURITY.md), [background tasks](https://github.com/openclaw/openclaw/blob/main/docs/automation/tasks.md), [memory-wiki](https://github.com/openclaw/openclaw/blob/main/docs/plugins/memory-wiki.md), [architecture](https://github.com/openclaw/openclaw/blob/main/docs/concepts/architecture.md), [Windows guide](https://github.com/openclaw/openclaw/blob/main/docs/platforms/windows.md), and [Android guide](https://github.com/openclaw/openclaw/blob/main/docs/platforms/android.md).

**External local Gateway vs. fork:** start with an adapter to a separately running, loopback-bound local Gateway if a later proof-of-fit is authorized. This preserves the upstream updater and avoids carrying a long-lived fork, while JARVIS can keep its own task and policy records. OpenClaw documents local and HTTP-compatible Gateway interfaces, and Windows Hub documents local MCP-server mode. However, its authenticated interfaces are powerful operator surfaces, not a narrow authorization boundary. A JARVIS adapter must not expose the shared Gateway credential to models or untrusted content, and must constrain calls before forwarding. A fork is justified only if an essential required boundary cannot be implemented at a supported adapter/interface and a maintained patch set is acceptable. ([Gateway API](https://github.com/openclaw/openclaw/blob/main/docs/gateway/openai-http-api.md), [Windows Hub MCP](https://github.com/openclaw/openclaw/blob/main/docs/platforms/windows.md), [security policy](https://github.com/openclaw/openclaw/blob/main/SECURITY.md))

### B — JARVIS-owned Python control plane with selective adapters

JARVIS owns goal/task schemas, policy decisions, memory/provenance, model routing, audit, and verification. Existing projects can be evaluated behind typed adapters; their runtime state does not become authoritative JARVIS state. A local OpenClaw Gateway may be one integration option, alongside direct official APIs or MCP, subject to narrow capability mapping and credential isolation. LangGraph, OpenHands SDK, Letta, and Open Interpreter may inform or serve specialized future components, but none is adopted as JARVIS's control plane by this ADR.

This fits the architecture and avoids rebuilding every mature channel. The costs are adapter development and compatibility/security testing, and the possibility that a desired component cannot fit a sufficiently narrow interface. All of this remains to be validated; no component was installed or integrated in Phase 00.

### C — Build all required integrations ourselves

JARVIS would own the entire implementation and could design every API around its policy and task semantics. It would also carry all work for Windows automation, Android pairing, communication APIs, durable execution, persistence, update compatibility, and security fixes. There is no Phase 00 evidence that this ownership advantage outweighs the engineering and maintenance burden. Reconsider it only if existing interfaces cannot meet a concrete security, privacy, license, or functionality requirement.

## Decision

Recommend **B: a JARVIS-owned Python control plane with selective adapters**. Keep JARVIS as the source of truth for policy, task state, memory contracts, and verification. Prefer adapters to separately running/local components where they preserve least privilege and clear data ownership. Evaluate an external local OpenClaw Gateway before considering any fork; do not grant it broad permissions merely to gain channel coverage.

This recommendation fits the full vision better than choosing only for speed to the first demo: it leaves room for local or remote models, an Android client, typed tool APIs, explicit memory provenance, and replaceable integration/runtime components without surrendering core semantics. “Zero mandatory recurring cost” is achievable only as a design constraint, not a guarantee of zero operating cost: local execution uses existing hardware/electricity/network, and any later hosted model, messaging service, relay, or hosting choice may cost money. The default must fail closed rather than silently switch to paid services.

## Trade-offs and risks

- B defers channel breadth until adapters exist; a user-facing feature may arrive later than under A.
- Adapter credentials and translation code can weaken a boundary if treated as transparent pipes. JARVIS must authorize each capability and retain audit/results itself.
- An external OpenClaw Gateway is feature-rich but not a JARVIS permission engine. Its shared-secret operator API must remain local/private and be wrapped narrowly.
- A Python core does not prove that local inference fits 8 GB RAM. No model weights, runtime, latency, or memory benchmark was used here.
- Android call screening metadata, a default-dialer role, controlling calls, and reading call audio are distinct. Actual OS version, vendor build, SIM/provider behavior, Bluetooth route, and permissions need checks on the user's phone. No autonomous cellular call or recording capability is claimed.
- Connectivity from outside the home network needs authenticated encryption and device revocation. A private VPN such as WireGuard is a possible no-hosted-service approach, but endpoint reachability/NAT and setup still need design; do not publicly expose the JARVIS API.
- Provider messaging APIs, model APIs, and account entitlements can change, require user scopes, or impose costs. None was configured or tested.

## Reversal criteria

Reconsider A if a bounded, no-paid proof-of-fit shows that an external local Gateway can safely expose the required Windows/Android/channel capabilities through narrow interfaces, while JARVIS can maintain authoritative task, policy, memory, audit, and verification state outside it. Consider a fork only if a required trust boundary or API cannot be achieved through supported interfaces and the owner accepts upstream merge/security maintenance.

Reconsider B in favor of C if official APIs/adapter surfaces cannot meet a concrete data-locality, least-privilege, license, or long-term support requirement and the custom integration can be tested and maintained. Reconsider the selected orchestration strategy if local measurements on the actual 8 GB laptop fail the task latency/RAM acceptance criteria, or if durable-recovery fault tests show the custom state machine is too costly or error-prone and a licensed, self-hostable runtime demonstrably fits without taking ownership of JARVIS policy.

## Verification plan

No runtime tests or benchmarks were run in this research-only phase. Before any implementation or integration, separately authorize and design a proof-of-fit that uses mock/local data and no paid endpoints: confirm Windows and Android pairing on the actual devices; test adapter capability filtering and credential handling; simulate restart/retry around a non-idempotent action; verify memory provenance/correction/deletion; and measure idle/peak RAM and task latency on the stated laptop. Test the phone's Android API level, roles, call state, audio route, and capture limits independently. Do not download model weights just to complete this ADR.
