# JARVIS Master Architecture — Baseline

## Principle
JARVIS owns its control-plane semantics: goals, durable tasks, permissions, memory contracts, model-routing policy and completion verification. Models propose; policy code authorizes; tools execute; observations establish actual outcomes.

## Logical flow
```text
Windows UI / Android companion
             |
      Authenticated API
             |
  JARVIS control plane
  (goals, context, devices, policy, audit)
             |
      Intelligence gateway
  (adapters, routing, structured output, evaluation)
             |
      Durable agent runtime
  (planning, task graph, checkpoints, bounded recovery)
             |
      Typed tool registry
  (browser, files, commands, Windows UI, integrations)
             |
   Observations -> Verifier -> Task result
             |
     Memory / project knowledge
```

## Starting deployment
A Python modular monolith on Windows, SQLite when persistence is added, FastAPI and a responsive local interface. Do not start with microservices, a large vector database, Docker agents, large local models or a phone emulator.

## Boundaries
- Provider adapters do not own task state or permissions.
- Model output does not grant tool permissions.
- Actions have typed inputs, explicit capabilities, limits and observable results.
- Local-first data; no remote model receives sensitive context unless explicitly authorized.
- No paid fallback; quotas must fail closed.
- Untrusted web pages/files/messages cannot override system policy.
- Cellular call control/audio is a tested feasibility question, not an assumed Android capability.

## Accepted architecture direction
Phase 00 is accepted. Option B is the approved direction: JARVIS owns its control plane, including task state, permissions, model-routing policy, memory contracts and verification. OpenClaw remains a potential external integration behind a selective adapter; it is not the authoritative JARVIS control plane. Recheck fit, license, security and maintenance before reusing or embedding any external component. See [ADR 0001](../decisions/0001-architecture-choice.md) for the decision and trade-offs.

## Phase 08 owner credential lifecycle prerequisite

- `DeviceStore` schema v4 persists an expiry and credential generation for owner bearer credentials, plus a metadata-only credential audit ledger. The trusted `Settings.owner_credential_lifetime_days` defaults to 30 days and accepts 1–365 days. New owner pairing, owner rotation, recovery, and migration establish or increment the generation; companions retain their existing independent revocation lifecycle.
- Owner authentication requires a parseable, timezone-aware expiry strictly later than the current UTC clock; the credential is rejected exactly at the expiry instant. There is no leeway: a fast host clock expires credentials early, and a slow, rolled-back, or manipulated system clock can extend their effective lifetime. Operators must maintain a correctly configured UTC host clock. No independent trusted time source or persisted monotonic clock is used, so changing system time can also distort the rotation limiter.
- Before v2 or v3 migration, the store verifies there is at most one owner row. A database with multiple owners fails clearly and the migration transaction rolls back rather than selecting or rewriting an owner. The schema's partial unique index enforces this invariant during normal pairing.
- `DeviceService.rotate_owner_credential()` authenticates the current bearer and requires the server-stored OWNER role. `DeviceStore` uses `BEGIN IMMEDIATE` and checks that the owner remains active, the stored digest still matches, and the credential is not expired before atomically replacing the digest and expiry. The same transaction enforces a durable rolling limit of five successful rotations per owner per hour by counting immutable rotation audit events. An over-limit request returns 429 with `Retry-After`, changes no credential, and records no success event. The API does not trust forwarded-client headers. The API route reveals the new token once and disables caching. Device role and reported capabilities never provide owner authority.
- Successful rotation and host-local recovery append an audit event in the same SQLite transaction as credential replacement. The record contains UTC time, event type, owner ID, actor class, origin, and success outcome; it excludes all credential material. Database triggers reject update/delete and the application provides no audit-mutation operation. This protects against routine application changes, not direct modification by a host principal with database write access.
- Local lost/expired-token recovery is an operator CLI (`python -m jarvis.devices.admin`), not a network route. It requires an interactive terminal, exact confirmation, and OS-level access to the configured device database. It warns that terminal output contains a secret and must not be captured in shell transcripts, logs, screenshots, or shared recordings before showing the token once. Software cannot prevent terminal capture. The trust anchor is the host operator and filesystem account; no independent recovery identity or hardware-backed secret exists. Recovery rotates an existing active owner and cannot create or un-revoke an owner.
- The rotation limit is stored implicitly in successful immutable audit events and is concurrency-resistant because checks and credential replacement occur under the same immediate transaction. A system-clock jump forward may prematurely expire credentials and clear the rolling window; a backward change can extend credential validity or prolong the limit. Correctly maintained host UTC time is required. A local process that can reach the loopback API can still cause request and SQLite load; forwarded headers do not change its identity or budget.

## Phase 08 task authorization foundations

- `TaskSubmissionPolicy` is an injected trusted contract. It receives an authenticated device ID and a validated task proposal, and must return an explicit allow decision with a device-bound `AuthorizationContext`. The task layer does not infer grants from a device role or self-reported capabilities. A missing policy, denied decision, mismatched principal, revoked device record or policy exception fails closed.
- `TaskRuntime.submit_device_task()` evaluates that policy before creating a plan. `TaskStore` persists the goal, task plan, device owner, idempotency key and request digest in one SQLite transaction. A retry with the same device, key and request digest returns the original plan; reusing that device's key with different content returns a conflict. This guarantees idempotent task creation only; it does not guarantee exactly-once dispatch or external effects.
- Owned tasks cannot be run or controlled through the legacy `run_task()`, `pause_task()`, `resume_task()`, `cancel_task()` or `reconcile_step()` entry points. The object-based `run_authorized_task()` compatibility method now fails closed. Internal execution uses `run_authorized_task_async()` with a fresh bearer credential, the existing `DeviceService.authenticate()` check, durable ownership comparison, and the persisted typed action. Device-scoped status reads use `TaskStore.get_task_plan_for_device()` (or `get_task_for_device()` for the task record); unknown and other-device task IDs return the same not-found result.
- `LocalDeviceTaskGrantPolicy` reads the local operator's versioned JSON allowlist on every decision. `Settings.device_task_grants_path` defaults to `data/local/device-task-grants.json`; a missing file, empty ID list, malformed or unsupported content, duplicate or invalid IDs, and read failures deny. No device IDs are included by default. The policy issues only `system:status:read` to an exact listed device for the empty-argument `jarvis.status` action; its decision ID includes a deterministic revision of the validated grant set. JARVIS does not currently record grant-file edits in a durable audit log; those changes remain under local operator/configuration management. `DispatcherBackedTaskRunner` is implemented as a class, and `TaskRuntime.run_authorized_task_async()` supports it when supplied with the required dependencies. The runner reauthenticates and reauthorizes, then calls the existing asynchronous `ToolDispatcher`, which retains policy, validation, approval and audit checks. The dispatcher must use the exact `DeviceTaskToolPolicy` instance type bound to its own registry. Request text, model output, memory, device role, and reported capabilities never select a tool or create a grant.
- An owned attempt and its action digest, authenticated device ID, and authorization fingerprint are persisted in SQLite. A transactional dispatch claim reduces duplicate dispatch for the same attempt. Dispatcher audit events carry the same typed correlation fields, but `InMemoryToolAuditSink` events are not durable across process restarts. An interrupted or post-dispatch uncertain attempt reaches reconciliation and must not be blindly retried; SQLite does not provide exactly-once external execution.
- The `main.py` lifespan opens the separate file-backed `TaskStore` at `Settings.task_database_path`, defaulting to `data/local/tasks.sqlite3`, and privately stores task application services after successful initialization. When a `DeviceService` exists, it composes `TaskRuntime`, separate submission and dispatch policies, `DispatcherBackedTaskRunner`, and a `ToolDispatcher` whose dedicated registry contains only `jarvis.status`, guarded by `DeviceTaskToolPolicy`. If no `DeviceService` exists, the authorized runner is absent. The task store is closed during lifespan teardown; SQLite access remains on its creating thread. The runtime's legacy runner is optional, and legacy execution fails before task state or attempts change when it is absent.
- Submission and dispatch use independent operator-managed policies. The submission policy reads `Settings.task_submission_grants_path`, defaulting to `data/local/task-submission-grants.json`; its strict version-1 allowlist has no device IDs by default and permits only empty-argument `jarvis.status`. Every submission, including an idempotent replay, requires a fresh valid bearer and current policy authorization. A new task returns 201; same-device/key/content replay returns 200; changed content under that key returns 409. `Location` and `Cache-Control: no-store` are set. Missing, empty, malformed, duplicate, unsupported, or unreadable policy data produces generic 503; a valid but nonmatching device/action is denied. Submission writes only the task plan and does not invoke execution. Its policy revision is not persisted as task provenance.
- The app registers `GET /health`, `GET /ready`, device routes `POST /devices/pair`, `GET /devices/me`, `PATCH /devices/me/capabilities`, `POST /devices/pairing-codes`, `POST /devices/owner-credential/rotate`, `GET /devices`, and `DELETE /devices/{device_id}`, plus `POST /tasks`, owner-scoped `GET /tasks/{task_id}`, `GET /tasks/{task_id}/events`, owner-only `POST /tasks/approvals/{approval_id}/decision`, and task-owner `POST /tasks/{task_id}/resume` and `POST /tasks/{task_id}/cancel`. Task status and event reads authenticate the active bearer on each request and use the task ID plus authenticated device ID in the owner-scoped lookup; unknown and foreign task IDs share the same not-found response. There is no initial task-execution, grant-management, or background-execution route. Production task execution remains gated for a separately reviewed milestone.
- `GET /tasks/{task_id}/events` polls the existing append-only TaskStore event log. `after` is an exclusive persisted event-ID cursor (default 0); each nonzero cursor must identify an event belonging to the requested task, and a cursor beyond that task's latest event is rejected. `limit` defaults to 50 and is bounded to 1–100. Events are returned in ascending ID order. `next_cursor` is the last returned event ID, or the supplied cursor for an empty page; `has_more` indicates a further event was present at query time. Repeating a cursor replays events after it, so clients should de-duplicate by event ID and advance the cursor only after processing a page. Successful responses are `no-store` and expose only event ID, type, task/step IDs, state transition fields, and occurrence time; internal metadata is omitted. Polling is read-only.
- Task cancellation is limited to eligible zero-attempt tasks owned by the authenticated task device. It atomically changes eligible task and step states, revokes pending and approved-but-unconsumed approvals, and appends the related TaskStore audit events in one TaskStore transaction. The task-owner bearer, expected device identity, active state, role and applicable credential expiry are validated under the DeviceStore reservation, which remains held through the TaskStore commit. An ineligible/repeated cancellation or a start/resume that commits first returns HTTP 409 without partial cancellation. DeviceStore and TaskStore are separate SQLite databases: the reservation protocol serializes credential changes through the TaskStore commit but does not provide cross-database atomicity or recall an action already consumed and in flight.

- The owner-scoped task status JSON exposes `task_id`, canonical task `status`, the established compatibility field `state` (same persisted `TaskState` value), timestamps, progress, task-level `result`, and ordered `steps`. `progress.completed_steps` counts persisted succeeded steps and `progress.total_steps` is the persisted plan size. Task-level `result` is the validated `StatusOutput` only for a single-step task whose persisted action is exactly empty-argument `jarvis.status`; it is `null` for multi-step tasks, so no ambiguous aggregation is implied. Each step reports its persisted `state`, dependency IDs, attempt count/limit, bounded attempt history (number, outcome, safe error code, start/finish timestamps), latest-attempt summary, timestamps, and its own permitted result under the same exact-action and `StatusOutput` validation rule. Reconciliation is visible through persisted task/step states and `outcome_unknown` attempt records. Attempt IDs, action arguments, authorization bindings, digests, and checkpoint internals are not exposed.
- Approval lifetime is configured by `JARVIS_APPROVAL_LIFETIME_MINUTES`, default 5 and bounded to 1–60 minutes. Owner decisions reserve the approving owner's active credential, expiry, and generation. Resume separately reserves both the approving owner and the task-owning resumer: it validates the approval-owner generation and the resumer's presented bearer digest, expected task-owner ID, active status, role, and owner expiry if applicable under one DeviceStore `BEGIN IMMEDIATE` reservation. Current task dispatch grants and tool definition are resolved from that trusted task-device record inside the reservation and revalidated immediately before TaskStore commit. Rotation, recovery, and companion revocation use the same DeviceStore write lock, so SQLite serializes them across connections and processes. The TaskStore commit is the approval decision/consumption linearization point; a revocation that commits first prevents consumption, while a later revocation cannot recall the already-consumed in-flight action. A fresh bearer and current dispatch grant are checked again before dispatch. This protocol does not make the two database commits atomic. Lock acquisition and transaction waits are bounded by SQLite's 5-second busy timeout and fail closed. Approval is never restored after consumption, and a claimed interrupted attempt follows existing reconciliation rules. The current app registry still contains only `jarvis.status`; approval does not broaden the tool allowlist or add shell execution.
- The task API provides read-only status, narrow submission, owner decision, task-owner resume, and task-owner cancellation routes, but no initial execution route, grant-management workflow, or background worker. Every resume requires a fresh task-owner bearer and current grant checks; stored ownership alone does not authorize it. The owner-generation reservation ends after TaskStore commit, so a later credential change cannot recall the action already considered in flight; current task-owner revocation and dispatch policy are checked again before dispatch. No cross-database atomic commit or atomic revocation with external tool execution is claimed. Local grant-file edits have no durable rollback history or JARVIS audit record. Submission policy provenance is not persisted. Dispatcher audit events remain in-memory, and uncertain outcomes must not be blindly retried. Notification events, offline queue/state, Android client, and listener changes are not implemented; the server remains loopback-only.
