# Threat Model

## Assets
Private files, source code, account credentials, model credentials (if later added), conversations, memory, task artifacts, contact information, phone notifications and permission settings.

## Threats
- Prompt injection in websites, documents, email and tool output.
- Accidental deletion/modification by generated commands.
- Credential leakage into Git, logs, screenshots or agent prompts.
- Unauthorized message/email sending.
- Overbroad Windows/mobile permissions.
- Unexpected model API/cloud charges.
- False claims that a task completed.
- Duplicate external actions after retry/restart.
- Background work/recording without consent.

## Initial controls
- Private GitHub repository; `.env` and local data ignored.
- No secrets in code or coding-agent prompts.
- Bind development server to `127.0.0.1`, not `0.0.0.0`.
- Typed tool allowlists; no arbitrary shell by default.
- Policy is separate from model reasoning.
- Approval for high-impact/irreversible operations.
- Timeouts, bounded retries, idempotency where possible, and audit events.
- External content is untrusted.
- No paid fallbacks; no billing-enabled API keys for initial build.
- Stop/cancel controls and explicit device capability status.
- Verify actual Android/telephony support before claiming call handling.

## Phase 04 Pass A: tool boundary

- Tool definitions are registered by trusted application code and declare typed input and output schemas, required capabilities, read/write classification, bounded timeout, maximum result size, and audit fields.
- Registry registration is a trusted application initialization operation; constructing a dispatcher seals the registry, after which its registration API rejects changes while lookups remain available. Model-generated requests and untrusted tool content cannot register or replace definitions. This lifecycle does not prevent arbitrary trusted-process code from mutating private internals directly.
- Tool requests and arguments remain untrusted proposals. Request data cannot supply a principal, capabilities, policy decision, or execution policy.
- Authorization is evaluated separately using a caller-provided trusted context. Missing context or required capabilities denies dispatch by default. WRITE definitions also require the dedicated `tool:write` capability; READ definitions do not.
- Dispatch emits structured events for authorization decisions, execution start, success, validation failures, timeouts, and execution failures. Events contain timestamps, tool/principal identity when available, access class, stable reason codes, and duration where applicable. Raw arguments, results, credentials, and exception text are excluded.
- Audit sink failures fail closed before executor invocation. A denied request remains denied even if its denial event cannot be recorded. A sink failure after execution is surfaced as a typed audit error; it cannot cause an automatic retry in this dispatcher.
- The provided in-memory sink is not durable; its events are lost when the process exits. No durable audit storage is implemented.
- Pass B1 adds a local status tool and workspace list/read/create tools. The status result reports only that the local control-plane tool responded and explicitly says external services were not checked; it makes no network requests.
- Workspace tools require an absolute root injected by trusted initialization. Requests cannot select the root. Listing is nonrecursive, examines at most 10,000 directory entries, returns at most 100 sorted regular file names, and omits symlink entries. Reads accept strict UTF-8 regular files up to 65,536 bytes. Creation accepts UTF-8 content up to 32,768 bytes and uses exclusive creation; existing files are never overwritten and parent directories are not created.
- Workspace paths reject absolute, drive-qualified, UNC, traversal and redirected components; returned paths are workspace-relative and filesystem errors are normalized by the dispatcher. Initialization checks the supplied root itself before resolving it, rejects symbolic links and Windows reparse points, and compares the original and canonical directory identities before retaining the canonical root. Operations also recheck that the retained root still has the same filesystem identity. These checks detect ordinary root substitution and many initialization races, but they do not bind later path-based opens to a directory handle. A hostile local process may still replace workspace entries between a check and a read or create operation; such concurrent filesystem replacement is not eliminated by this implementation. The configured workspace must be trusted against concurrent local mutation. Workspace symlink tests were skipped in the current Windows environment because its policy prevented symlink creation; these symlink scenarios were not dynamically tested.
- File contents are returned as untrusted data and do not grant permissions or authorize further operations. Workspace creation requires both `workspace:write` and `tool:write`.
- Higher-risk tool definitions may require approval and supply a static safe summary. After input validation and authorization, the dispatcher creates a pending request from that metadata and the trusted principal, records an approval-requested audit event, and returns a typed approval-required error without invoking the executor. Requests contain no raw arguments. If recording the audit event fails after request creation, the caller can receive an error while the pending request remains in memory; the tool executor is not invoked. The in-memory request service is non-durable and loses requests on process restart. No decision is accepted, request IDs do not authorize execution, and no post-approval execution path exists.
- These tools are only registered through trusted application initialization and are not wired into production routes. No arbitrary shell, network or personal-account tools, external side effects, approval UI, trusted decision channel, persistent approval storage, expiry workflow, or execution-after-approval workflow is implemented. Pass B2 does not establish production readiness or complete Phase 04.

## Phase 05: local memory

- Memory records are local SQLite data with typed record kind, source, source time, confidence, provenance, scope, sensitivity, permission, validity, expiry, version and lifecycle metadata. User-confirmed, model-inferred, tool-observed and legacy-unknown provenance remain distinct. A user-confirmed provenance label does not itself grant retention or retrieval permission; retrieval defaults to allowed permission only, exact permitted scopes, bounded sensitivity, current lifecycle/validity and explicit opt-in for inferred records.
- Retrieval policy is enforced in parameterized store queries for both ID lookup, full-text search and metadata filtering. An inaccessible ID yields the same not-found-style result as a missing ID. Separate management contexts are required for creation, correction and deletion and are checked against scope and sensitivity. The application must supply trustworthy access contexts; this package does not authenticate principals or define a user-facing consent workflow.
- Corrections use a transaction and expected-version check, preserve the prior row as superseded, and create a linked replacement. Deleting a replacement does not make an older superseded record current. Deletion removes the row and search index entry, but SQLite row deletion does not guarantee forensic erasure from database pages, WAL files, backups or storage media. No memory content is written to application audit logs by this subsystem.
- Memory migrations use a separate version ledger and preserve existing rows. Records whose legacy governance cannot be trusted receive inaccessible scope, restricted sensitivity, unspecified permission and legacy-unknown provenance; ordinary retrieval cannot expose them. Migrations are transactional and tested for idempotence and data preservation. No backup/restore or migration rollback tooling is provided beyond SQLite transaction rollback on failure.
- Search uses SQLite FTS5 when available; otherwise a parameterized, bounded `LIKE` search fallback is used. Neither path uses embeddings or external services. Local SQLite files are not encrypted by this feature, and file-level access remains dependent on operating-system controls.
- Phase 07 connects retrieval to the task runtime only through an explicitly injected context assembler and context-aware step-runner method. Memory content is not passed to a runner through the legacy interface. No model call, API route or production application flow is added. Retention rules beyond explicit validity/expiry, backup handling, authenticated user authorization, secure deletion, and operational review remain future work; this implementation is not a production-readiness claim.

## Phase 06 Pass B–D: browser research tool integration

- Trusted application initialization may register the `browser.research` definition and map its returned executor into a dispatcher. The definition accepts the typed `ResearchRequest`, returns validated `ResearchResult` metadata, is classified READ, and requires the separate `browser:research` capability. The fetcher and its exact-host allowlist are supplied by trusted initialization; request data cannot change that policy. Registration is explicit and does not wire routes or install a global tool.
- The existing dispatcher enforces default-deny authorization before fetch execution, input/output validation, configured timeout and result-size limits, safe failure normalization, and structured audit events. A missing authorization context or missing `browser:research` capability prevents the fetcher from being called. No approval is required for this read-only definition.
- Retrieved page text and source metadata remain untrusted external data. Instruction-like content does not grant capabilities, authorize another registered tool, or invoke a tool. Any other operation needs its own trusted registration and explicit capability grant. There is no autonomous loop that interprets retrieved content as instructions.
- Dispatch audit events contain the tool name and safe decision/outcome metadata but omit request arguments, including the URL, and omit fetched page text and output. The default in-memory audit sink is non-durable; records are lost when the process exits.
- Pass C strengthens destination checks with a trusted exact-IP allowlist for every allowed hostname. Every DNS answer is rejected unless it is globally routable and explicitly listed for that same hostname; connections use the validated numeric address, with no fallback to ordinary hostname resolution, proxies or redirects. TLS uses a fresh `ssl.create_default_context()` with the system trust store, certificate and hostname verification, and a TLS 1.2 minimum. `SSLContext.set_ciphers()` applies `ECDHE+AESGCM:ECDHE+CHACHA20:!aNULL:!MD5:!RC4:!CBC` to TLS 1.2 and earlier only. It does not configure TLS 1.3 cipher suites, which retain platform/OpenSSL defaults. Each fetch creates a fresh HTTPX client and transport with keep-alive disabled. These code controls reduce DNS-rebinding exposure and prevent a changed, unapproved DNS answer from becoming a connection target.
- Trusted per-host IP lists can become stale when a site's CDN changes addresses. The application owner must verify and deliberately update those entries; the code does not automatically widen the policy. The allowlist still permits an explicitly approved endpoint that later becomes hostile or compromised. Host and network egress policy are needed to restrict unusual routing and provide broader containment. These controls do not establish comprehensive SSRF protection or prove retrieved page claims true or safe.
- Trusted IP allowlist governance checklist: approve each hostname and its exact public IP list from a trusted source; verify the site/operator relationship and that HTTPS identity matches the hostname; reject private, loopback, link-local, reserved, multicast, unspecified and unverified addresses; review address changes deliberately and never auto-expand from DNS; periodically review or expire stale approvals; and apply host/network egress firewall policy independently.
- Resolver injection is trusted configuration and must be callable; resolver failures, timeouts, malformed answers, unapproved IPs and mixed answer sets fail closed with safe typed errors. The caller's DNS wait is bounded before TCP setup, but cancelling the default async `getaddrinfo` await may not stop its executor-thread operation immediately. A nested `asyncio.wait_for` around the same operation would not itself stop that work. Tests inject resolver output and mock the TCP/TLS transport boundary; no live DNS or TLS handshake occurs.
- Code reduces risk through exact host-to-IP checks, HTTPS/TLS verification, numeric-IP pinning, redirect/proxy suppression and bounded timeouts. Those controls cannot constrain unusual host routing, host compromise, or every network path; OS and network egress policy remain independent defense layers.
- Phase 06 was accepted after independent review and merged into `main` through PR #4. The integration still has no production route wiring, model API calls, search service, external summarizer, additional tool, retry loop or automatic follow-on execution; acceptance does not establish production readiness.

## Phase 07: memory retrieval and task context assembly

- The task runtime can receive an optional `MemoryContextAssembler`, which uses the existing `SQLiteMemoryRetriever` and store-enforced filters. A trusted runtime caller supplies `RetrievalContext`; absent or empty scopes return no memories. The store continues to enforce allowed permission, exact scope, sensitivity ceiling, inferred-memory opt-in, current lifecycle, validity and expiry. Access contexts are caller-supplied trusted inputs, not authentication or proof of user identity.
- The assembler performs bounded lexical retrieval and deterministic ranking, deduplicates candidates by record ID, and applies hard limits of 8 records, 4,000 serialized characters per record and 12,000 characters for the rendered context. Oversized records are skipped rather than truncated. The assembled JSON preserves the original record and provenance fields and marks retrieved content as untrusted data.
- A configured runtime delivers context only through `execute_with_memory_context`. It does not add capabilities, alter the authorization context, register tools, invoke a dispatcher, or automatically save retrieved text. Retrieval failures are normalized to a safe runtime error before a step attempt starts; the task remains retryable and the runner is not called. Existing runner behavior is unchanged when context assembly is not configured.
- Task-memory context assembly has no model/provider call, API route, browser-to-memory persistence, or user authentication flow. Any future runner that forwards memory to a model must keep it separate from privileged instructions and use only an explicitly permitted provider. Context and memory storage remain local to the existing SQLite store; SQLite deletion does not guarantee forensic erasure. No production-readiness claim is made.

## Phase 08 Pass A: device identity and pairing foundation

- The device service is a trusted in-process foundation and is not wired to FastAPI routes. It does not change the listener; the API continues to bind only to `127.0.0.1`. No remote device can use this service over the network in this pass.
- Bootstrap pairing requires an explicitly supplied code of at least 32 characters; there is no built-in default. The bootstrap code is consumed once and only its SHA-256 digest is stored. An active owner device can create five-minute, one-use companion pairing codes and can list or revoke companion devices.
- Each pairing generates a random bearer token returned once in a secret wrapper. SQLite stores only its SHA-256 digest. Tokens have no expiry in Pass A; revocation is persistent and irreversible through this service. The owner device cannot revoke itself. Loss of the owner credential has no recovery/reset workflow in this pass.
- Device names, platform and reported capabilities are untrusted metadata. Reported capabilities do not grant tool, task or API permissions and must never be used as authorization evidence. Protected API routes, request authentication, task synchronization, event delivery, offline state and Android client behavior are not implemented yet.
- The database contains device metadata and credential digests in plaintext SQLite pages; file access depends on operating-system controls. No encryption-at-rest or forensic-erasure guarantee is made.

Update this document whenever an integration or permission is introduced.
